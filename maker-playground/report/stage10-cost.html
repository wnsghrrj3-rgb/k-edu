R71 — 미리보기 실빌드 비용 실측·해소

R68 부터 3회 이월된 과제. 추정 없이 실제 크롬에서, 실제 폰 사진 규격(12MP JPEG 30장 · 원본 합 47.8MB)으로, 실제 클릭 한 번의 비용을 쟀다. 측정 하니스 perf71.mjs, 저장본 _perf71-before.json · _perf71-after.json.

1. 무엇이 문제였나

사진 30장에서 ★ 를 한 번 누르면 화면이 1,980ms 얼어붙었다. 범인은 엔진이 아니었다 — 실빌드(buildSmart)는 275ms 로 전체의 1/7 이었고, 나머지는 원본 data URL 이 매 렌더마다 HTML 로 다시 흘러간 값이다. 사진 한 장이 1.7MB 인데 30장이면 51MB, 목록·미리보기 마크업이 붙어 렌더 한 번에 65MB 짜리 문자열이 만들어지고 브라우저는 그걸 다시 파싱하며 12MP 이미지 30장을 매번 새로 해독했다.

「★ 클릭 블로킹」은 화면이 실제로 멈춰 있는 시간이다. 후(後) 값은 처음 누르는 경우(캐시가 절대 못 맞는 조건)로 쟀다. 「요약 갱신 완료」는 화면이 멈추는 시간이 아니라, 「구성을 다시 세는 중…」이 실제 숫자로 바뀌기까지의 시간이다.

3. 처방 세 갈래

  • ① 썸네일 1회 축소 — 목록에 그리는 그림만 320px 로 줄여 m.thumb 에 담는다. 원본 m.src 는 손대지 않으므로 만들어지는 영상 화질은 그대로다(T18·T20 이 지킨다). video2 의 thumb() 은 m.thumb || m.src 로 한 갈래만 넓혔다 — 축소본이 없으면 종전과 같다.
  • ② 결정론 캐시 — 같은 입력·같은 씨앗이면 buildSmart 는 언제나 같은 답을 낸다(R66 T1 계약). 캐시가 돌려주는 값은 직전에 실제로 돌린 그 빌드 결과이지 어림수가 아니다(T11). 서명은 사진마다 붙인 이름표(_uid, 비열거)로 만든다 — 2MB data URL 을 해싱하면 아끼려던 비용을 그대로 다시 낸다.
  • ③ 부분 갱신 — 역할 하나 바꾸자고 목록 전체를 다시 그리면 썸네일 30장을 매번 새로 해독한다(중간 실측 680ms). 바뀐 것은 칩 하나·행 하나·요약 한 줄뿐이므로 그 셋만 고친다(T27).
정직성 계약 — 비용을 줄이는 일에서 제일 쉬운 유혹은 「실제로 안 세고 대충 말하기」다. 그래서 요약이 도는 동안 옛 숫자를 그대로 두지 않고 「구성을 다시 세는 중…」 이라고 먼저 말한 뒤 실제 숫자로 바꾼다(T30·T31). 입력이 하나라도 바뀌면 반드시 다시 센다(T5~T10·T13).

4. 안 쓴 길

축소 디코드(createImageBitmap + resizeWidth)도 같은 사진으로 대조했으나 이 환경에서 더 느렸다(10장 2,128ms vs Image+canvas 1,761ms). 빠른 쪽만 남겼다.

6. 남은 한계

  • 업로드 직후 첫 렌더는 여전히 원본을 싣는다(30장 455.6ms / 58,514KB, 딱 한 번). 사진을 곧바로 보여주는 값과 맞바꾼 것 — 축소본이 준비될 때까지 회색 칸을 보여주는 쪽이 더 빠르지만 그건 다른 약속이다.
  • 축소 자체가 30장에 1586.8ms 든다. 배경에서 사진마다 손을 놓으며 돌지만 그동안 목록은 원본을 그린다.
  • 실빌드 하한은 그대로 — 처음 누르는 역할 변경은 결국 한 번은 세야 한다(30장 224.5ms). 화면이 안 멈출 뿐이다.
  • 측정은 헤드리스 셸 · 데스크톱 뷰포트(1440×900) 기준이다. 실제 학교 태블릿·저사양 기기 실측은 미실시.
